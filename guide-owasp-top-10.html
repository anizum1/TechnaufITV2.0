The OWASP Top 10, explained for business owners

The OWASP Top 10 is the closest thing the industry has to a shared list of what actually goes wrong in web applications. Here is what each item means without the jargon — and which ones are your vendor's problem versus yours.

Technauf engineering·14 min read

What it is, and why you should care even if you don't build software

The Open Worldwide Application Security Project publishes a periodically updated list of the ten most critical web application security risks, compiled from real-world vulnerability data. It has become the default reference point: auditors ask about it, cyber insurance questionnaires reference it, and enterprise customers put it in vendor security reviews.

If your business runs a customer portal, an e-commerce site, a booking system, or any internal web application — whether you built it or bought it — this list describes the ways it most commonly fails. You do not need to fix these yourself, but you do need to know enough to ask your developer or vendor the right questions.

A note on version: OWASP revises the list every few years and the categories shift between editions. Confirm which edition your auditor or customer is asking about before you answer a questionnaire — the numbering is not stable across releases.

1. Broken access control

The application does not properly enforce what each user is allowed to see or do. In practice this is the customer who changes an invoice number in the URL and sees another customer's invoice, or the standard user who reaches an admin page simply by knowing its address.

It consistently ranks at or near the top because it is easy to get wrong and rarely caught by automated scanning — the software works exactly as coded, it just trusts the user too much.

Ask your vendor: is authorisation checked on the server for every request, or does the interface just hide buttons the user shouldn't press?

2. Cryptographic failures

Sensitive data is not protected properly in transit or at rest: traffic served over plain HTTP, passwords stored with weak or no hashing, database backups sitting unencrypted, or encryption keys checked into the same repository as the code.

Ask your vendor: how are our customers' records encrypted at rest, and where are the keys held?

3. Injection

Untrusted input gets interpreted as a command. The classic example is SQL injection, where text typed into a form is treated as part of a database query and can be used to read or destroy data. Cross-site scripting is the same failure in a different place — attacker-supplied text executed as code in another user's browser.

This is largely a solved problem technically: parameterised queries and proper output encoding prevent it. It persists because legacy code and rushed features skip them.

4. Insecure design

The application was built without thinking about how it could be abused. No amount of careful coding fixes a feature that was a bad idea — a password reset flow that only asks for a birthday, or a checkout that trusts a price submitted by the browser.

This is the category that requires business input, because only you know which workflows would be damaging if abused.

5. Security misconfiguration

Default credentials left in place, verbose error messages exposing internals, unnecessary features enabled, cloud storage buckets set to public, admin interfaces reachable from the internet. Not a coding flaw — a settings flaw, and one of the most common causes of real incidents.

This one overlaps heavily with what a managed IT provider should be handling for you.

6. Vulnerable and outdated components

Modern applications are assembled from hundreds of third-party libraries. When one has a published vulnerability and nobody updates it, your application inherits that vulnerability — and attackers scan the internet for exactly these known, unpatched versions.

Ask your vendor: do you maintain a software bill of materials, and what is your SLA for patching a critical vulnerability in a dependency?

7. Identification and authentication failures

Weak login handling: no protection against automated password guessing, session tokens that never expire, credentials accepted from lists already leaked in other breaches, or multi-factor authentication that can be trivially bypassed.

The single highest-value fix here is enforcing MFA and checking passwords against known-breached lists.

8. Software and data integrity failures

The application trusts code or data from sources it cannot verify — an auto-update mechanism with no signature checking, or a build pipeline that pulls in unvetted dependencies. This is the category that covers supply-chain compromise, where attackers reach you by compromising something you install rather than attacking you directly.

9. Security logging and monitoring failures

The attack succeeds and nobody notices. Without adequate logging and someone actually reviewing it, breaches are typically discovered weeks or months later — often by an outside party rather than the victim.

This is the category businesses most consistently underinvest in, because it produces nothing visible until the day you desperately need it.

10. Server-side request forgery

The application can be tricked into making requests on the attacker's behalf, reaching internal systems that should never be exposed. Increasingly relevant in cloud environments, where an internal metadata service can hand out credentials to whoever asks from inside the network.

Who is responsible for what

Split the list into three buckets and the ownership question becomes manageable:

  • Your software vendor or developer — access control, injection, insecure design, integrity failures, SSRF
  • Your IT provider — misconfiguration, outdated components, authentication enforcement, logging and monitoring
  • You, as the business — deciding which data matters, defining who should have access, and insisting somebody is accountable for each item above

Three questions worth asking this quarter

  1. When was our web application last tested against the OWASP Top 10, and can I see the report?
  2. If someone exploited our portal tonight, which log would show it and who reads that log?
  3. Which third-party libraries are we running, and how quickly do they get patched?

If nobody can answer these, that is the finding — and it is a better starting point than any product purchase.
